# 第一版不支持请求间共享状态

- 状态：`已接受`
- 日期：2026-09-18
- 关联：[Mock 服务选型调研](../../research/mock-server-landscape.md)、[示例文档清单与二进制下载场景](../demo-document-catalog.md)

## 背景

Mock 产品普遍把请求间状态当核心能力：WireMock Scenarios、Mountebank `inject(request, state)`、MockServer 回调、json-server 自动 CRUD、Mockoon CRUD 模式与 data buckets。本产品的候选范围一度包含"最小共享键值存储"。

第一版需要圈定功能边界，而共享状态会连带引入生命周期、并发隔离、持久化选型三个子问题。

## 决策依据

1. **已验证场景是无状态的。** 设备文档的 manifest 与 download 各自独立读取同一外部元数据接口，彼此零耦合，请求间无任何数据传递（`plans/demo-document-catalog.md` 第 3 章）。
2. **同一实现中 `db.json` 是空占位 `{}`。** 自动 CRUD 与状态能力在该场景里一点没用上，用到的全部是"数据源 + 变换 + 文件转发"。
3. **共享状态的定义要求数据没有别处可存**（mock 生成的 token/id、客户端上传后读回、跨请求进度）。第一版不承诺这三类场景。

## 决策

第一版的数据来源限定为两类：本地静态数据文件、外部真实上游接口。不提供请求间共享状态。

2026-09-18 补充：响应推进（同一接口按调用次序改变响应）同样不进第一版。它与共享状态共用同一条边界——"一个请求的处理不依赖前一个请求"，并写入第一版不做清单；v2 考虑以声明式响应序列或脚本 `callCount` 的形式加入。

第一版明确不支持：凭证签发与校验、POST 后 GET 读回同一记录、依赖上一请求结果的分支响应。

## 后果

**正面**：接口语义退化为单请求封闭函数，可预测、可离线断言，配置无需考虑隔离与清理。

**负面（接受）**：有状态客户端流程无法测试，例如登录取 token 再访问、异步任务轮询、上传后按 id 下载。这是已知功能缺口，不是遗漏。

**约束（不可破坏）**：不得把状态塞进 transform 的闭包或变量。必须保持"一个请求的处理不依赖前一个请求"，否则第二版加真状态时会与这些事实上的隐藏状态冲突。

## 替代方案

- 最小共享键值存储加过期（覆盖凭证与写后读，成本是一个内存 map 加隔离设计）：因无需求证据而推迟。
- 完整资源生命周期（可编程版 json-server）：因 json-server 已占据该位置、且在已验证场景中未被使用而否决。
