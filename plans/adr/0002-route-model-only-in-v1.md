# 第一版只实装路由模型，资源派生推迟为同一引擎的预设

- 状态：`已接受`
- 日期：2026-09-18
- 关联：[ADR 0001](0001-no-shared-state-in-v1.md)、[Mock 服务选型调研](../../research/mock-server-landscape.md)

## 背景

产品受 json-server 启发，但它卖的是另一种东西：json-server 的 `db.json` 是资源模型——数据文件的形状自动派生出一整套 REST 路由（`GET /users`、`GET /users/:id`、过滤、分页、排序），不需要逐个声明接口。而已验证的真实场景（设备文档）用的是路由模型——URL、数据源、变换、响应逐项声明，`db.json` 是空占位。

两者是两种配置模型：资源模型问"我有哪些数据"，路由模型问"我有哪些接口"。同时实装会形成两个引擎，配置语法、错误语义、文件能力都要实现两遍。

## 决策依据

1. 已验证场景全部是路由模型：自定义路径 + 外部元数据 + 变换 + 文件转发。
2. 同一实现中自动 CRUD 零使用，资源模型没有需求证据。
3. 资源模型一旦独立成引擎，文件 I/O 与变换能力要在两套模型里各做一遍，成本翻倍且行为容易分叉。

## 决策

产品内部只有一个执行模型：**路由 = 匹配 + 数据源 + 变换 + 响应**。

第一版只提供显式路由声明。资源派生模型推迟，且将来实装时必须是路由模型的预设生成器——把数据文件编译成一批普通路由，不得新增第二个执行引擎。

## 后果

**正面**：单一语义，变换、文件、错误处理对所有接口行为一致；配置能力边界清晰。

**负面（接受）**：最常见的"快速 mock 一个列表接口"场景，入门门槛高于 json-server。需要靠预设模板补偿，模板本身也编译为普通路由。

**约束（不可破坏）**：任何新能力都不得绕开"匹配 + 数据源 + 变换 + 响应"四段模型另起一套执行路径。

## 替代方案

- 纯路由模型、不保留资源派生（拒绝：放弃最低门槛入口）。
- 纯资源模型（拒绝：无需求证据，且双引擎成本）。
- 第一版就实装资源派生（拒绝：范围膨胀，无验证场景）。
