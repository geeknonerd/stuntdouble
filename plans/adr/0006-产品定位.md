# 产品定位：对接真实外部依赖的联调假服务

- 状态：`已接受`
- 日期：2026-09-18
- 关联：[ADR 0001](0001-第一版不支持共享状态.md)、[ADR 0003](0003-第一版采用完全脚本化与多语言运行时.md)、[ADR 0004](0004-脚本能力只经宿主函数提供.md)

## 背景

三条候选定位：

- **A 通用 Mock Server**：与 WireMock / Mockoon / Prism 正面竞争"所有需要 mock HTTP 的开发者"。
- **B 联调真实外部系统的假服务**：目标用户是需要对接真实外部依赖（上游是别人的系统、内部文件服务、无法控制的第三方接口）的后端与集成开发者。
- **C AI 编码代理的测试后端**：作为 agent 集成测试的 mock 后端。

## 决策依据

1. 已验证场景（读外部元数据接口 → 生成 CSV 清单 → 按 code 匹配并转发 PDF）就是 B 的形态，没有一条证据支持通用静态 stub 场景。
2. 通用静态 stub 是红海：Postman、Mockoon、Prism 免费且成熟，第一版没有 GUI、没有热重载、没有 Admin API，正面竞争没有胜算。
3. 现有差异化组合（单二进制、零运行时依赖、脚本化变换、外部取数与文件一等公民、沙箱）恰好是 B 场景的痛点：WireMock 要写 Java 扩展，json-server 要写 middleware，两者都不是配置级能力。
4. C 场景（agent 测试后端）对"零运行时依赖 + 确定性 + 二进制文件"的要求与本产品天然重合，做 B 的过程顺带覆盖，无需专门投入。

## 决策

**主定位 B**：面向"需要对接真实外部依赖"的后端与集成开发者的联调假服务，用于本地与 CI。

**C 作为顺风加成**：不专门为 agent 场景做功能，但不做阻碍该场景的设计选择。

**A 只做兼容**：不追求通用 mock 场景的功能对齐（GUI、热重载、Admin API、资源模型自动 CRUD 均不在第一版优先级内），也不做针对性竞争。

## 后果

**正面**：功能优先级有了统一裁决标准——"这个能力是否服务于对接真实外部依赖的联调"；与通用产品的对比压力下降。

**负面（接受）**：市场规模小于通用方案；需要向用户解释定位（"这不是另一个 json-server"）；通用场景用户会失望，应在文档中明确边界。

**约束**：新增功能与"通用 mock 便利性"冲突时，按 B 场景裁决；通用能力的引入必须证明它能服务 B 场景。

## 替代方案

- A 通用路线（拒绝：红海、无证据、第一版无竞争性差异）
- C 单独立项（拒绝：市场未验证；作为顺风加成保留，不单独投入）
