# 上游失败语义：默认透传，传输层失败才造错误码

- 状态：`已接受`
- 日期：2026-09-18
- 关联：[ADR 0003](0003-script-first-multi-runtime.md)、[ADR 0004](0004-host-functions-only-sandbox.md)、[示例文档清单与二进制下载场景](../demo-document-catalog.md)

## 背景

已验证的 json-server 实现把失败分成了两类固定映射：元数据接口非 2xx → `502 metadata_bad_gateway`；PDF 地址失败 → `502 pdf_bad_gateway`；文档不存在 → `404`。那是单个接口的手工决策。

产品化后每次上游调用都要回答同一个问题：Mock 该把上游的失败原样交给客户端（保真），还是统一翻译成自己的错误码（干净）？脚本化架构让"由脚本决定"成为可能，因此需要定下默认。

## 决策依据

1. 产品定位是替代真实上游。客户端要测"上游返回 404 时我怎么处理"，若默认翻译成 502，就测不到真实链路，且这种默认无法通过配置改回来。
2. 已验证实现的做法是脚本决策的结果，不是引擎行为。它把 `document_id` 不存在判成 404、上游失败判成 502，是业务判断；这种判断应当属于脚本，而不是焊在引擎里。
3. "有响应"和"没响应"是天然分界：有响应说明上游活着，语义归上游；没响应说明依赖断了，语义归 Mock 服务自己。

## 决策

**以"是否拿到 HTTP 响应"为唯一分界。**

1. **拿到响应（含 4xx/5xx）**：视为数据。宿主不抛错，脚本自行决定。默认**透传上游状态码**；脚本可 `ctx.respond()` 改写为任意语义。
2. **传输层失败**（DNS、连接拒绝、TLS、超时）：抛异常给脚本，可 `try/catch`；未捕获则返回 `502` + `{error: "upstream_unreachable", request_id}`。
3. **脚本自身异常**（语法/运行时/panic）：未捕获则返回 `500` + `{error: "script_error", request_id}`；堆栈只进服务端日志。
4. **脚本未调用 `ctx.respond()`**：视为脚本逻辑错误，返回固定错误码，不静默 200。
5. **超时预算**：脚本总超时是硬上限（默认 10 秒，可配置），上游超时不独立设更长值，实际生效 = `min(剩余脚本时间, opts.timeout_ms)`。实现会从剩余预算中预留一小段回复余量（最多 100ms 或剩余预算的 10%），确保上游超时能作为传输层失败返回 502 `upstream_unreachable`，而不是与脚本硬超时竞态。
6. **重试**：默认不重试；`opts.retries` 显式开启，上限 3 次，且只对传输层失败生效。

**可观测性**：

- 每请求一条结构化日志：`request_id`、命中路由、脚本耗时、上游调用链、最终状态码、错误分类。
- 默认不记录请求体/响应体，仅记录大小与白名单 header，避免 token/Cookie 泄漏。
- 诊断开关（暂名 `--verbose`）打开后，`502`/`500` 响应附加 `detail` 字段；文档标注不得用于共享环境。
- 分片落地：T4 先记录最终状态码与错误分类；上游调用链、耗时明细与 `--verbose` detail 在 T7（#10）补齐。

## 后果

**正面**：保真优先，"上游挂了"与"上游说没有"两类信号在客户端侧不会混淆；错误映射策略下沉到脚本，引擎不需要枚举业务分支；`request_id` 把对外错误与对内日志钉在一起。

**负面（接受）**：脚本作者必须显式处理上游非 2xx，忘记处理就会把上游错误码直接透给客户端；错误码集合变大（引擎码 + 上游码并存）。

**约束**：客户端永不看到堆栈、上游响应体或内部地址。

## 修订（T6，#9）：`ctx.http.pipe` 的非 2xx 语义

`ctx.http.pipe` 无法沿用"拿到响应即视为数据"的默认透传：body 由宿主直接流向客户端，脚本拿不到字节，也就无法在检查之后改写状态。修订后的语义：

- 上游 2xx：立即开始流式转发，客户端状态默认透传上游 2xx 状态（普通路径 200，Range 路径 206 等）。
- 上游最终非 2xx：抛出可捕获错误 `upstream_http_error`，由脚本决定客户端错误码（demo 映射为 502 `pdf_bad_gateway`）。未捕获时为 500 `script_error`，不会伪装成 502 `upstream_unreachable`。
- URL 无法解析或协议不是 http/https：抛出可捕获错误 `upstream_url_invalid`；重定向链无法继续（超过 3 跳或 `Location` 不可用）抛出可捕获错误 `upstream_redirect_error`；allowlist 拒绝仍为 `script_error`，不得伪装成上游故障。
- 传输层失败：语义不变，抛 `upstream_unreachable`。

原因：流式路径上"有响应即数据"无法同时满足"脚本拥有业务错误码"；把非 2xx 表现为可捕获错误，是脚本能在开始写响应体之前决定客户端错误码的唯一方式。

流已经开始后，读取中断只能截断客户端 body，无法再改写状态；demo 文档中"PDF 读取失败 → `pdf_bad_gateway`"因此只覆盖开始流之前的失败。

## 替代方案

- 全部失败统一映射为固定错误码（拒绝：丢失保真，且脚本已能自行实现）
- 默认对传输失败自动重试（拒绝：静默重试掩盖客户端要测的超时行为）
